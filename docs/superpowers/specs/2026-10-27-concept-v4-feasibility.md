# 概念稿 v4 可行性评估

2026-10-27。评估对象：概念稿 `.impeccable/mocks/canvas/index.html`（提交 `e43f7bc`），对照分支 `feat/block2-daemon` 上的代码和 v2 规格（`2026-10-24-calsync-v2-product-design.md`）。

这是一份决策文档，只回答“能不能做、谁来用、做不到怎么办”，不是实施计划。

## 0. 结论

- **概念稿里大部分功能都能做。** 数据和同步引擎基本都有，缺的主要是“写”的一侧：安全写配置、暂停/放行、按日期查询日程。这几项本来就在 ② 块的待办里。
- **有几处措辞要改，因为 calsync 实际上做不到概念稿说的那样：**
  1. “已送达”只代表日程写进了 iCloud 服务器，calsync 不知道家人的 iPhone 有没有显示，也不知道提醒有没有响。
  2. “有人把时间改成了 16:30”：能知道副本被改了、改成了什么，但不知道是谁改的。
  3. “授权失效，通常是密码改过或授权被撤销”：Google 不告诉原因。
  4. 删除线路时“已同步的日程会从目标日历移除”：现在没有这个清理操作，要新做，而且是一次大批量删除。
- **对 Agent 来说，最缺的不是改日程，是核对。** 按规格，Agent 本来就直接写 Google（§1.1）。它缺的是“写完以后确认送到了”这半圈：`calsync trigger --wait` 加上一个按日期查询日程、带送达状态的命令。这一对是最该先做的 Agent 能力。
- **有些步骤只能由人完成，这是刻意的设计**，比如 Google 授权、输入 iCloud 密码、扫码配对、开启写权限。Agent 能做的是打印命令或链接，交给人去完成。
- **需要你决定的有 3 件**，见 §6。

## 1. 怎么读下面的表

- **界面**：概念稿里这个功能长什么样。
- **CLI（给 Agent）**：
  - `已有`：命令现在就能用；
  - `要补`：建议新增的命令；
  - `不做`：不适合做成命令，后面写了原因。
- **后端**：只有三种结论。
  - **已有**：数据和逻辑都在，接上就行；
  - **要补**：能做，但要写新代码；
  - **做不到**：受外部服务或设计边界限制，只能变通。
- 所有 CLI 命令都带 `--json`。改东西的命令都支持 `--dry-run`：先显示配置会怎么变、同步会发生什么，不写入。这条是规格 §1.3 的延伸。

## 2. 给 Agent 的主线：写、送、核对

规格 §1.1 的分工是：AI 助手把日程写进 Google，calsync 送到家人设备，人在界面上确认结果。所以 Agent 的典型流程是：

1. 用 Google 日历连接器写入或修改日程（不经过 calsync）；
2. `calsync trigger --wait --json`：立刻同步一轮，等它结束，返回这一轮改了什么；
3. `calsync events --from 2026-10-27 --to 2026-11-03 --json`：列出这段时间的日程，每条带上各目标日历的送达状态。

目前第 2 步只做了一半：`trigger` 发起同步后立刻返回（本地接口回 202），不等这一轮结束。`upcoming` 也只能看接下来几小时，不能按日期范围查。把这两处补上，Agent 就能自己核对“家人的提醒有没有送到”，不用人去看界面。

界面上的“修改日程”是给人用的。CLI 也可以提供 `event edit`，但 Agent 已经有更直接的路，所以排在后面。

## 4. 只能由人完成的步骤

下面这些步骤不是 CLI 做不到，而是不应该交给 Agent 做：

| 步骤 | 原因 | Agent 能做什么 |
| --- | --- | --- |
| Google 授权（浏览器同意页） | 必须是账号本人点同意 | 运行 `calsync auth <账号>`，把输出的链接或命令转告给人 |
| 输入 iCloud App 专用密码 | 密码不应经过 Agent；Apple 也要求两步验证 | 告诉人运行哪条命令；密码由终端的隐藏输入接收（`getpass`） |
| 生成 App 专用密码 | 要登录 Apple 账户网页 | 给出操作步骤 |
| 扫码配对新设备 | 要实体设备 | `calsync web pair` 打印链接和二维码 |
| 开启 Google 写权限 | 要重新授权 | 同第一行 |

统一做法：CLI 遇到要人参与的步骤时，不卡住、也不报含糊的错。它返回一个结构化结果，比如 `{"needs_human": true, "command": "calsync auth work-google", "reason": "..."}`，Agent 把这个结果转告给人。

## 5. 做不到的事和变通

1. **确认日程真的出现在家人的 iPhone 上、提醒真的响了。** iCloud 不提供设备端回执。变通：
   - 措辞从“已送达”改成“已送达 iCloud”；
   - 可选“回读核对”：写入后再取一次，确认对象在、提醒（`VALARM`）在、内容哈希一致；
   - 写入家人自己的 iCloud 账号时，提醒照常触发：这和第一期实际运行的情况相同（E5 已由它证实）；写在自己账号再共享给家人时，提醒不会跟过去（v3 §13 实验 A）。
2. **知道是谁改了 iPhone 上的副本。** 只能知道被改了、改成了什么。措辞用“在 iPhone 上被改了”，不说“有人”。
3. **授权失效的确切原因。** Google 不说。变通：列出常见原因，并先确认 OAuth 应用是否处在测试状态（见 §3.4）。
4. **秒级送达。** 不做 Google 推送（D2），默认每 60 秒检查一次。变通：界面改日程后、Agent 写完后，立刻 `trigger`。
5. **在明文 HTTP 下输入密码。** 这是刻意不做的（D10）。变通：显示终端命令。
6. **改只读日历或别人邀请你的日程。** Google 拒绝。变通：提前识别并置灰。
7. **改 iCloud 副本。** 单向同步（D5）。变通：改原件。
8. **来源不是 Google，或目标不是 iCloud（CalDAV）。** 现有架构不支持，以后另加适配器。

## 6. 决定（2026-10-27）

1. **放行被拦下的删除：Agent 和人都可以放行（用户决定，与规格 §4.3 一致）。**
   - 背景：防误删在第一期就有。一轮同步要删的副本超过 10 个或超过一半时，这条线路整轮暂停，什么都不删，等人确认。现在只能用 `calsync run --allow-deletes` 放行，常驻进程运行时还得先停掉它；规格计划的 `approve` 还没做。
   - 场景：calsync 跑在家庭服务器或 VPS 上，用户平时让 Agent 改 Google 日历。Agent 按用户要求批量删除后，calsync 拦下并推送通知；用户再让 Agent 放行，或者自己打开界面放行。放行是一个工具，谁用都行。
   - 为了让这个工具好用、不出错，`approve` 要做到：
     - 拦下时推送通知，写明哪条线路、要删多少个、前几个标题；
     - `calsync blocked --json` 列出被拦下的删除，含完整的待删列表，让 Agent 先核对再放行；
     - 放行只对这一次被拦下的那批删除有效：如果放行前又多出了要删的日程，这次放行作废，需要重新确认；
     - 放行后再推送一条通知，并记进活动记录（谁放行的：界面还是命令行）。
2. **修改日程：做。** 和界面放在同一个块里，作为它的最后一段，见 §8。
3. **OAuth 应用处在“测试”状态，授权每 7 天失效一次。** 用户认为现在的设计够用：授权一断，“重新连接”就会显眼地出现。另一个好处是，开启写权限所需的重新授权可以和每周的重新连接合在一起，不额外打扰。

## 7. 对后端的补齐清单

按依赖顺序排列：

1. 安全写配置、热加载、配置改动记录（规格 §4.4、§4.5）。所有设置页都依赖它。
2. 暂停、恢复、放行。
3. 按日期范围查询日程，带送达状态（`events`），以及 `trigger --wait`。六种日历视图和 Agent 核对都依赖它。
4. 缓存各账号的日历列表；CLI 的 `status` 补上下次检查时间；界面要知道“一轮刚开始”。
5. 副本摘要和改动的字段级摘要（对比表、“原来是 10:00”）。
6. Bark 通知（规格 §4.6）。
7. Google 写权限和修改日程。

## 8. 排期

| 阶段 | 内容 | 为什么排在这里 |
| --- | --- | --- |
| A：② 块后半（后端） | §7 第 1–6 项；`calsync service install` | 界面上的每个按钮都要先有后端操作；CLI 和界面共用同一层操作，做完 A，Agent 就能用全部配置和核对命令 |
| B：③ 块（界面） | 按概念稿 v4 重写网页：地图和右侧面板里的全部配置、六种日历视图、日程详情、活动、设置、接入向导；浏览器自动化测试 | 依赖 A 的接口 |
| C：③ 块最后一段（修改日程） | Google 写权限（按账号开启）、修改原件、只改这一次 / 改整个系列、保存后立即同步；CLI `event edit` | 依赖 B 的日程详情和 A 的 `events`、`trigger --wait`；风险最高（第一次写 Google），放在最后、单独审查 |

每个阶段结束时都要经过审查、测试，再合并。“这次及以后”、新建、删除和拖动日程不在 C 里，C 做完后再定。
