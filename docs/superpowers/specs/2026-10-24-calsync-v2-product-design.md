# calsync 第二阶段设计：全量镜像、常驻服务与网页界面

- 日期：2026-10-24
- 状态：草案，待评审
- 作者：Aryous 与 Claude

## 0. 摘要

本阶段把 calsync 从"一个定时运行的命令"变成"一个可以放心交给家人用的产品"。工作分三块，按顺序进行，每块各自写实施计划、各自评审和上线：

| 块 | 内容 | 依赖 |
| --- | --- | --- |
| ① 同步引擎调整 | 默认全量同步；字段策略可配置；目标端被改动时按来源改回（真正的单向镜像） | 无 |
| ② 常驻服务与通知 | `calsync daemon`、本地控制接口、配置热加载与安全写入、改动记录、Bark 通知 | ① 的配置格式 |
| ③ 网页界面第一版 | 总览、线路详情、同步记录、接入向导、扫码登录、即时配置 | ② |

## 1. 产品定位与原则

### 1.1 定位

AI 助手（例如 ChatGPT 的 Google 日历连接器）把日程写进 Google；calsync 负责把它送达家人的设备；用户在这里确认结果。

界面不是用来编辑日程的。它回答三个问题：

1. **通不通**：每条同步线路是否正常。
2. **改了什么**：来源最近发生了哪些变化，calsync 同步了哪些。
3. **到没到**：目标日历里接下来会出现什么事件，带什么提醒。

### 1.2 设计原则

1. **平时安静，出事才响。** 一切正常时，首页只有一句状态；需要处理的事以卡片和推送出现。
2. **说结果，不说技术细节。** 首页不出现令牌、状态码等词；细节在第三层。
3. **每个数字都能点开看证据。** "更新了 15 个"可以展开到具体事件。
4. **只在修复时提供操作。** 界面不编辑事件；操作按钮只用于重新授权、确认删除、立即同步、暂停、小幅修改线路设置。
5. **接入要手把手。** 从零接入 Google 和 iCloud 的向导单独设计。
6. **边界可见。** 同步了什么、没同步什么、为什么，都要说清楚；凡是"少了"，都要给出解释。

### 1.3 Agent 友好

- calsync 的能力集中在 Python 的一层**核心操作**里（查状态、列出接下来的事件、改线路设置、立即同步、确认删除、暂停与恢复等）。命令行、网页界面都是这层操作外面的壳，能做的事一致，校验只有一处。
- **命令行是 Agent 的主要接口**：
  - 所有命令支持 `--json`，输出稳定的结构化结果；
  - 退出码保持 v3 §12 的约定；
  - 仓库提供一份写给 Agent 的命令行使用说明。
- HTTP 接口只为网页界面服务，不作为面向 Agent 的公开接口承诺。
- 不做 MCP 服务。本地 MCP 相对命令行没有增益；远程 MCP 需要公网 HTTPS 和 OAuth，会把含家人私人日程和账号授权的服务暴露在公网上。以后有明确场景再单独决定。
- 隐私：`--json` 和界面会显示事件标题。它们输出到标准输出或浏览器，不进入日志文件，符合 v3 的隐私不变量。用户若把输出交给云端 Agent，标题会随之离开本机。这一点写进命令行说明。

## 2. 已定决策汇总

| # | 决策 | 理由 |
| --- | --- | --- |
| D1 | 默认全量同步；时间范围降为可选的高级设置 | "同步"在用户心里就是完整复制；Google 侧本来就全量拉取，代价只在首次写入 |
| D2 | 默认检查间隔 60 秒；不做 Google 推送 | 推送需要公网 HTTPS 地址；60 秒轮询空闲时每轮只有 3–4 个请求 |
| D3 | 不复制的字段改为可配置，默认值见 §3.2 | 工程取舍应作为用户可见的设置 |
| D4 | "目标端被改动时怎么处理"是线路的正式设置；第一版只开放"以来源为准"，并真正实现改回 | 同步应保证目标与来源一致；"保留目标端修改"会让 AI 的后续修改送不到，暂不提供 |
| D5 | 双向同步往后排，单独做一个阶段；届时参考 vdirsyncer 与 Syncthing 的冲突处理 | 冲突、误删、回环、字段映射、权限升级都需要专门设计 |
| D6 | 界面在手机和电脑上都要好用；看的页面以手机为主，配置页面以电脑为主 | 两种场景都常见 |
| D7 | 远程访问交给 Tailscale 或 Surge Ponte；calsync 只在一个端口上提供带登录的网页 | 不自己处理公网安全；不绑定某个隧道工具 |
| D8 | 界面在普通 HTTP 下完整可用；不依赖只有 HTTPS 才能用的浏览器功能 | Ponte 只透传流量，浏览器看到的是 HTTP |
| D9 | 登录用带密钥的链接（扫码配对），浏览器换得长期 Cookie；可一键重置密钥 | 不用记密码，在 HTTP 下可用；参考 magpie |
| D10 | 密码和凭证只能在本机（`localhost`）或 HTTPS 访问时填写；其他情况改为显示终端命令 | 敏感信息不在明文 HTTP 上传输 |
| D11 | 通知第一版只做 Bark，另留通用 webhook | 用户在 iPhone 上；Bark 配置最简单 |
| D12 | 配置仍是一份 TOML 文件，界面、命令行、手工编辑共用 | 可读、可手改、可用 Git 管理 |
| D13 | 网页前端用 Preact + htm，免构建，随包分发，调用同一套 JSON 接口 | 项目保持只有 Python 工具链；组件化便于做表单和向导 |
| D14 | 远程登录 Google 时，向导让用户把跳转后的地址粘贴回来（待实测） | Google 的设备码方式不支持日历权限，页面显示授权码的方式已停用 |
| D15 | 首页在手机上把连接图放在最前，时间线在后 | 一眼看清"什么连着什么"；连接图本身带状态 |
| D16 | 界面不识别、不提示共享日历 | calsync 无法可靠判断一个日历是否被共享；相关限制只写在 README |
| D17 | 向导不区分"同步给自己"还是"同步给家人" | 两者都只是"再连一个 iCloud 账号" |

## 3. 块①：同步引擎调整

### 3.1 默认全量同步

- `rules[].window` 变为可选。省略时表示全量：来源日历里的所有事件（无论过去还是未来）都同步，修改和删除照常跟随。
- 设置了 `window` 时，行为与 v3 相同，并在界面和 `calsync status` 中明确显示范围、范围外的数量和原因（原则 6）。
- 无限重复的系列在目标里仍是一个对象，不展开。系列的时间跨度计算沿用现有的有界展开（`SPAN_EXPANSION_LIMIT`）；全量模式下，窗口检查对所有跨度都视为相交。
- 首次全量同步的写入数等于来源系列数，此后每轮都是增量，空闲预算不变（v3 §8.1）。大日历的首次同步可能耗时较长，进度在 `calsync status` 和界面中可见。
- 防误删保护的分母改为线路内全部托管对象。

### 3.2 字段策略

每条线路新增 `fields` 设置：

```toml
[[rules]]
name = "family-schedule"
source = { account = "me-google", calendar = "家庭日程" }
target = { account = "family-icloud", calendar = "家庭日程" }
alarms = "copy"                      # 已有：copy | strip | 偏移数组
fields = { attendees = "notes", conference = "copy", content = "full" }
on_target_edit = "revert"            # 第一版唯一取值
```

| 字段 | 取值 | 默认 | 说明 |
| --- | --- | --- | --- |
| `attendees` | `"none"` / `"notes"` | `"notes"` | `notes`：在备注末尾追加"参与人：名字 <邮箱>, …"。不写 `ATTENDEE` / `ORGANIZER`，因此不会触发目标服务器发送邀请 |
| `conference` | `"copy"` / `"none"` | `"copy"` | 把会议链接写入 `URL` 属性，并追加到备注 |
| `content` | `"full"` / `"busy"` | `"full"` | `busy`：标题写"忙"，不写备注和地点，时间和提醒照常。用于把工作日历同步到个人日历 |

- 这些设置参与内容哈希：修改设置后，线路下的对象会被重写一次。
- "作为真正的参与人复制"（`ATTENDEE` 加 `SCHEDULE-AGENT=CLIENT`）不在第一版。要先验证 iCloud 是否遵守这个参数、不发邀请，见 §9 的 E4。
- 只同步 `popup` 类型的提醒；Google 的邮件提醒不同步。这一条写进 README 的边界说明。

### 3.3 目标端被改动时：按来源改回

**现状**：内容指纹 `X-CALSYNC-HASH` 写在正文里。iPhone 修改事件时通常原样保留这个字段，calsync 因此发现不了改动（v3 §2；严格 xfail 测试 `test_manual_target_edit_is_repaired`）。

**目标**：`on_target_edit = "revert"` 时，目标端对托管事件的任何修改，都会在下一轮被改回来源的版本；目标端删除的托管事件会被重新创建。

**做法**：

1. 记录"我们写入后的 etag"。PUT 响应带 `ETag` 时直接记录；不带时，在同一轮内对本轮写过的 href 批量取回 etag（只取 `getetag`，不取正文），使下一轮空闲时仍然只有检测请求。
2. 检测阶段报告某个托管 href 变化，且新 etag 不是我们记录的 etag 时，视为"他人修改"：读取正文。
3. 由正文重新解析出规范化的系列内容，计算"实际内容哈希"，与期望哈希比较；不一致就以来源内容重写。比较的是规范化后的内容，所以服务器自行添加的无关属性不会造成误判。
4. 目标端删除的托管 href：检测报告删除后，从缓存中移除；规划阶段发现期望存在但目标缺失，就重新创建。
5. 正文读不到或解析失败：按 v3 的保护规则处理，不覆盖、不删除，并记入改动记录。

**前置实验**（块①实施计划的第一个任务，结论回写 v3 §13）：

- E1：在 iPhone 上修改一个托管事件，读回正文，确认 `X-CALSYNC-HASH` 是否保留、etag 是否变化。
- E2：确认 iCloud 的 PUT 响应是否带 `ETag`（v3 §13 第 6 项）。

实验结果只影响第 1 步的取 etag 方式，不改变上面的总体设计。

### 3.4 文档

- README 新增"calsync 写入了什么"一节：说明资源名、`X-CALSYNC-RULE`、`X-CALSYNC-HASH` 的作用，以及哪些内容不同步。
- 删除 README 中"目标端修改会保留"的限制说明，严格 xfail 测试改为普通测试。

## 4. 块②：常驻服务与通知

### 4.1 常驻进程

- 采用 v3 §10.1 的设计（排他锁、周期不重叠、规则级失败退避、信号处理）。默认间隔 60 秒，抖动 10%。
- 每个周期开始时重置请求计数（v3 遗留问题：`RequestLog` 只增不减）。
- 部署：launchd 以 `KeepAlive = true` 运行 `calsync daemon`；`calsync service install` 生成并加载 plist，并移除旧的定时任务。迁移到 Mac mini 时，先在旧机器上 `calsync service uninstall`。

### 4.2 本地控制接口

- 常驻进程在状态目录下监听一个 Unix 套接字（权限 0600），提供与网页界面相同的 JSON 接口。文件权限就是授权，不需要密钥。
- 命令行在常驻进程运行时作为它的客户端：
  - 需要改变状态的命令（`trigger`、`approve`、`pause`、`resume`、配置修改）通过套接字执行；
  - 只读命令（`status`、`upcoming`、`changes`、`calendars`）可以直接读状态库（WAL 模式支持并发读）。
- 常驻进程不在运行时，命令行照常直接执行（与 v3 一致）。`calsync run` 在常驻进程运行时拒绝执行，并提示改用 `calsync trigger`。

### 4.3 新增和变化的命令

| 命令 | 作用 |
| --- | --- |
| `calsync daemon` | 运行常驻进程（含网页服务） |
| `calsync trigger [--rule R]` | 立即开始一个周期 |
| `calsync status [--json]` | 每条线路的状态、上次同步时间、待处理事项、同步范围 |
| `calsync upcoming [--hours N] [--json]` | 接下来的事件及其提醒和送达状态 |
| `calsync changes [--rule R] [--since T] [--json]` | 改动记录 |
| `calsync approve <rule>` | 放行一次被防误删机制拦下的删除 |
| `calsync pause <rule>` / `resume <rule>` | 暂停或恢复一条线路 |
| `calsync web pair` | 在终端显示配对链接和二维码 |
| `calsync web reset-key` | 重置密钥，所有设备需重新配对 |
| `calsync notify test` | 发送一条测试推送 |
| `calsync service install` / `uninstall` | 安装或移除 launchd 常驻任务 |

`approve` 的确认：在交互式终端里，要求输入线路名确认；`--yes` 可以跳过。命令行无法区分是人还是 Agent 在操作，所以这只是一道提醒，不是安全边界；真正的保障是防误删阈值，加上每次放行都会推送通知给用户。

### 4.4 配置的读取与写入

- **热加载**：常驻进程监视配置文件。文件内容的指纹变化时重新加载；新配置校验失败时保留旧配置，推送告警。常驻进程自己写入后，会记下新指纹，不会把自己的写入当成外部修改。
- **写入**（界面和命令行的配置修改共用）：
  1. 用 tomlkit 读取，只修改涉及的键，保留注释和格式；
  2. 用与 `calsync config check` 相同的校验检查修改后的完整配置，不合法则拒绝，并指出具体字段；
  3. 比较读取时的指纹与当前文件指纹，不同则拒绝，提示"文件已在外部被修改，请重新加载"；
  4. 把当前文件复制为 `config.toml.bak`，写入临时文件，再原子替换；
  5. 在改动记录中写入"谁改的"（界面、命令行或外部编辑）以及改动摘要。
- **不写进 TOML 的东西**：
  - 密码和令牌：在凭证后端，TOML 只写引用；
  - 界面密钥：在 0600 权限的文件里；
  - 会话、同步记录、改动记录：在状态库里。
- **多用户**：每个账号和线路可以带 `owner` 字段，默认 `admin`。如果将来要做多人共用，配置需要迁移到数据库，到时另行设计。

### 4.5 改动记录

- 状态库新增两张表：
  - `change`：每个周期内每个对象的动作（创建、更新、删除、改回、受保护、被拦截），字段为周期编号、线路、对象编号、动作、时间。
  - `config_change`：配置改动，字段为时间、操作来源、改动摘要。
- 标题不写入日志文件。显示时从来源镜像（0600 权限的状态库）中联查标题；对于已删除的事件，镜像中已经没有，所以在 `change` 记录里保存一份标题快照（同样只存在于状态库中）。
- 保留期：同步记录每条线路保留 500 个周期（与 v3 一致），改动记录保留 90 天。
- 受保护和不完整的系列、被拦截的删除标题，从 v3 中只存在于单次运行结果，改为持久化到这些表中（v3 遗留问题）。

### 4.6 通知

- 配置：`[notify] bark_url`（第一版）和 `webhook_url`（通用 JSON POST），`public_url`（通知里的链接指向的界面地址，可选）。
- 触发条件沿用 v3 §11：授权失效、防误删拦截、连续失败达到阈值、恢复。另外增加：配置热加载失败、`approve` 放行了删除。
- 同一问题在恢复前只推送一次。推送里带一句话说明和"打开"链接，跳转到界面中对应的页面。
- 推送失败只写日志，不影响同步。

## 5. 块③：网页界面第一版

### 5.1 技术架构

- **服务**：网页服务运行在常驻进程内，使用 Starlette + uvicorn，监听一个 TCP 端口（默认 `127.0.0.1:8766`，可配置为局域网地址），同时在 Unix 套接字上提供同一套 JSON 接口（§4.2）。
- **前端**：Preact + htm，免构建；库文件随 Python 包一起分发，不依赖外部 CDN。页面静态资源带内容哈希，长期缓存。
- **接口**：JSON 接口直接调用核心操作层，界面与命令行行为一致。
- **普通 HTTP 兼容**：不使用 Service Worker、Web Push、`navigator.clipboard`、`crypto.subtle` 等只在 HTTPS 下可用的功能；复制操作依次尝试 `navigator.clipboard`、`execCommand`，都失败时显示文字让用户手动复制。
- **外观**：参考 Keeper 的视觉语言（大量留白、服务图标、虚线连线）；支持深色模式，在首次渲染前应用主题，不闪烁。
- **多语言**：中文和英文，以英文原文为键。

### 5.2 访问与登录

- 默认只监听本机。局域网访问通过 `[web] listen = "0.0.0.0:8766"` 显式打开。
- **配对**：
  - `calsync web pair` 或界面设置页显示链接 `http://<地址>/?k=<密钥>` 和对应的二维码；
  - 浏览器打开后，服务器用常量时间比较校验密钥，签发 Cookie（`HttpOnly`、`SameSite=Lax`，HTTPS 下加 `Secure`，有效期 400 天），然后重定向到去掉密钥的地址；
  - 没有 Cookie 的浏览器看到"粘贴密钥"页面。
- **重置**：`calsync web reset-key` 或在设置页操作，所有已配对的设备失效。
- **允许的来源**：`[web] allowed_hosts`，例如同时允许 Tailscale 和 Ponte 的主机名。修改类请求校验 `Origin` 和 `Host`，防止跨站请求。
- **敏感信息输入**（D10）：只有页面来自 `localhost` 或 HTTPS 时，才显示密码输入框和凭证上传；其他情况下，这一步改为显示终端命令（例如 `calsync auth family-icloud`），完成后界面自动刷新状态。
- 远程访问方式（Tailscale 或 Ponte）写进 README，不由 calsync 安装或配置。

### 5.3 页面

**总览（首页）**

1. 顶栏：名称、总状态圆点、"立即同步"、菜单。
2. 一句话状态，例如"一切正常 · 1 分钟前同步 · 今天同步了 12 处改动"；有问题时改为"有 N 件事需要你处理"。
3. 待处理卡片（只在有事时出现）：每张一件事、一个按钮，例如授权失效 → 重新连接；删除被拦截 → 查看并确认；配置加载失败 → 查看原因。
4. 连接图：左边来源，右边目标（手机上改为上下排列），虚线相连。连线颜色就是健康状态，线上标注范围（"全部日程"或具体范围）。节点上显示上次同步时间和待处理数量。手机上连接图高度有上限，让下方时间线露出一截。
5. 接下来：未来 24 小时所有线路的事件，按时间排列。每行显示时间、标题、目标标签（按目标日历着色）、提醒、送达状态。点开查看来源与目标的对比。
6. 最近改动：两三行摘要，点开进入改动记录。

电脑上：状态和待处理卡片在顶部；下面左栏是连接图和最近改动，右栏是时间线。

**线路详情**

- 未来 7 天的事件时间线，含每个事件的提醒和送达状态。
- 最近改动（来自 `change` 表），例如"14:51–15:17 来源中 220 个事件被修改 → 已同步 15 个系列"。
- 设置：同步范围、提醒策略、字段策略、暂停或恢复、立即同步。即时保存，校验错误显示在对应字段旁；外部修改冲突时提示重新加载。
- 范围外和受保护的对象数量带说明，可以展开查看。

**同步记录**

- 每个周期一行：时间、耗时、请求数、创建、更新、删除、改回的数量、结果。
- 展开可以看到具体事件。错误用大白话说明原因，并给出修复按钮。

**设置**

通知（Bark 地址、测试推送）、访问（配对二维码、重置密钥、允许的来源）、配置文件位置、"撤销上次配置修改"。

**接入向导**

1. **连接账号**（可以重复，连接多个 Google 和 iCloud 账号）：
   - **Google**：分步图文说明如何创建自己的 OAuth 客户端（启用 Calendar API、同意屏幕设为正式发布、创建"桌面应用"类型凭证），上传凭证文件后当场检查类型，然后登录：
     - 页面在运行 calsync 的机器上打开时，走 v3 已有的本机回调，自动完成；
     - 其他情况，向导提前说明"登录后页面会显示无法打开，请把地址栏的完整链接复制回来"，用户粘贴后，calsync 从中取出 `code` 和 `state`，用同一个 `redirect_uri` 换取令牌。这条路径不受本机回调等待超时的限制。
   - **iCloud**：直达 Apple 生成 App 专用密码的页面；输入用户名和密码后，自动判断国际区或中国区，并列出日历。
   - 两者都受 §5.2 敏感信息输入规则约束。
2. **建线路**：选来源日历和目标日历；先预演，不写入，例如"将创建 17 个系列；目标日历里原有的 3 个事件不会被动"；确认后保存配置并开始同步。
3. **通知**：填 Bark 地址，发送测试推送。

### 5.4 数据从哪里来

| 界面内容 | 来源 |
| --- | --- |
| 线路状态、上次同步、待处理 | `run`、`alert`、`change` 表 |
| 接下来的事件 | 来源镜像；新增纯函数 `expand_instances(series, start, end)`，有界展开重复系列并应用单次改动和取消 |
| 每个事件的提醒 | 期望内容（应用提醒策略之后） |
| 送达状态 | 目标缓存中该系列的内容哈希等于期望哈希，且没有待改回的修改 |
| 最近改动 | `change` 表，标题从镜像或快照联查 |
| 范围外、受保护的对象 | 规划阶段的结果，持久化在 `change` 表 |

### 5.5 手机适配

- 断点：宽度不超过 760px，或触屏设备宽度不超过 1024px，使用手机布局。
- 手机上没有侧边栏，导航是顶部一排可横向滑动的标签。
- 可点击元素不小于 44px；输入框字号 16px，避免 iOS 聚焦时放大页面。
- 适配刘海屏和底部手势区的安全边距（`viewport-fit=cover`、`env(safe-area-inset-*)`）。
- 一行放不下时，次要信息折到第二行；数字卡片在手机上排成两列。
- 不做 PWA（Service Worker 在普通 HTTP 下不可用）。

## 6. 错误处理

- 核心操作沿用 v3 的错误分类（授权、配置、冲突、找不到、权限、临时错误）。界面把每一类映射成一句大白话和一个修复动作，例如授权错误 → "重新连接"。
- 配置写入失败（校验不通过、外部冲突、写盘失败）不改变现有配置，并在界面字段旁或命令行输出中给出原因。
- 网页服务出错不影响同步周期；同步周期出错不影响网页服务的可用性。

## 7. 测试

- **块①**：
  - 单元测试：字段策略的渲染与哈希、全量模式的规划、`expand_instances`；
  - Radicale 端到端测试：目标端修改被改回、目标端删除被重建、写入后无 ETag 时的 etag 取回；
  - 请求预算测试扩展到全量模式和改回场景：空闲周期预算不变；
  - `test_manual_target_edit_is_repaired` 改为普通测试。
- **块②**：
  - 常驻进程的调度、退避和信号；
  - 本地套接字接口；
  - 配置写入的五个步骤，包括冲突检测、注释保留、校验拒绝；
  - 热加载时忽略自身写入；
  - 用假的 Bark 服务测试推送的触发与去重。
- **块③**：
  - JSON 接口：在进程内对 ASGI 应用直接请求；
  - 登录：配对、Cookie、重置、`Origin` 校验；
  - 敏感信息输入：只在 localhost 或 HTTPS 下出现；
  - 界面：用 Python 版 Playwright 在 Chromium 和 WebKit 中运行，接口全部用假数据；在 360×760 的手机视口下检查页面无横向溢出、按钮不被截断、文字不被挤压，并在桌面视口下做同样检查；以普通 HTTP 打开页面，确认没有依赖 HTTPS 的报错。

## 11. 上线与迁移

1. 块①上线后，在本地配置中删除现有线路的 `window`，即可切换到全量同步；首次运行会补上此前在范围外的旧事件。
2. 块②上线后，用 `calsync service install` 替换现在每 5 分钟运行一次的 launchd 任务。
3. 迁移到 Mac mini 时，先在当前机器上运行 `calsync service uninstall`，再在 Mac mini 上安装，避免两台机器同时写同一个日历。
